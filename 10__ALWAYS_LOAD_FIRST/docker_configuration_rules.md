# docker_configuration_rules

适用：编写或修改 Dockerfile、compose 文件、`.env.example`、`.dockerignore` 时。

将这类任务视为“不可变构建产物、可变运行时状态、环境差异”三者的边界划分问题。核心失败模式不是 YAML 或指令语法写错，而是配置在作者机器上成立、换到目标环境就失效，或者把该持久化的状态固化进镜像、把该留在此环境的配置泄漏进仓库。先定边界——哪些进镜像、哪些挂载、哪些由环境注入——再落文件。

关切优先级：

- 优先：能不能起来（端口占用、网络连通、启动顺序依赖、挂载路径与属主权限）；数据会不会丢（命名卷 / bind mount / 容器可写层三者的取舍）；凭据是否落进镜像层、构建缓存或版本库。
- 其次：层序与缓存命中、基础镜像来源与体积；非 root 运行、健康检查、重启策略、资源与日志上限。
- 力求避免：为尚未明确的规模堆叠编排特性；写死主机名、绝对路径、浮动的 `latest` 标签。

展开方式：先列出这套配置成立所依赖的前提——目标运行时是单机还是编排、镜像从哪来、数据与密钥怎么注入、对外暴露面多大——缺失的以变量占位并同步列入 `.env.example`，不臆造具体值。按文件交付：Dockerfile、compose 文件、`.env.example`、`.dockerignore`，关键取舍就地以注释写一行理由，不另起解释段。给出一条最小可运行路径；生产加固项写成“在某处加某行”的形式，不重写成另一套配置。

产物视为最终交付。不写“我将……”“以下是……”“希望对你有用”等过程叙述或寒暄；产物内（含注释、括注）不出现关于本次改动、修订、差异、状态的说明——这类说明只在产物外给出。

遇到无法判定的情形：部署目标或数据归属不明，先给单机 compose 的最小可运行版并标 [待确认]；bind mount 与命名卷之间标 [另一解]；是否需要多阶段构建标 [依情况]，不默认套用。
